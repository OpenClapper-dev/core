# 10 · Conclusion: target model and build plan

Workshop [#337](https://github.com/OpenClapper-dev/core/issues/337). Status: **decided** (2026-11-23).

What the workshops add up to: one data model, one API, what happens to every part of today's app, and the order in which the rebuild is done. The decided pages ([00](00-principles.md)–[09a](09a-places.md), [I1](i1-interjection.md), [U1](ux-1-files.md)–[U6](ux-6-devices.md)) stay the specification; this page does not repeat them, it ties them together. [model.md](model.md) is the overview in one picture.

**Rule for the build** (owner, [U6](ux-6-devices.md)): the prototypes show the design, not the feature list. What today's app can do stays unless a page says it goes. Each build step takes its inventory from the current code and from `docs/features/`, and from the "Not prototyped" list of its UX page.

## Target data model

### One table for files

Everything is a file ([07](07-organisation.md)). So there is one `files` table, and what differs per type hangs off it.

| Column | Meaning |
| --- | --- |
| `id` | Client-generated UUID, as today |
| `root` | The project it belongs to, or the account home of a user |
| `type` | photo, collection, folder, canvas, shot, set, location, timeline, filter, optics preset, property definition, naming pattern, device, camera layout, and what extensions add (flow) |
| `name` | Generated by the type's naming pattern at creation; editable, not unique |
| `container` | The folder or collection it sits in; null at the top level |
| `internal_of` | The file it was made inside ([I1](i1-interjection.md)); null for an ordinary file |
| `fixed` | Desktop and Settings folders |
| `created_at`, `updated_at`, `created_by`, `deleted_at`, `deleted_with` | System properties and the recycle bin, as today's bin columns |
| `edit_lock` | Who edits it and until when: one lock per file, whichever window edits ([U4](ux-4-timeline.md)) |
| `body` | The type's own document as JSON, checked by shared code on every save |

What goes into `body`, and what gets a table of its own because the server has to search or join it:

| Type | In `body` | Own table or columns |
| --- | --- | --- |
| Photo | Readout of device and lens | `photos`: the three stored objects (original, preview, thumbnail) with sizes, time taken, pixel size, angle of view, source, device, the frame at capture |
| Collection | Order, colour | Membership is `container` on the photo |
| Canvas | Surface, objects with groups, looks, comments | `frames`: every frame of every canvas (values or preset and focal length, position, the picture mark), so "this lens is in use" is one query ([02](02-optics.md)); the render and thumbnail objects |
| Shot | Progression (items, timing, overlay, default frame) | Content and progression items in `refs` |
| Set, location | – | Content in `refs`; the position is a property value |
| Timeline | Chapter markers, default hold time | Clips in `refs`; `projects.master` holds the order of timelines |
| Filter | The query | – |
| Optics preset | Format, multiplier, squeeze, delivery, lenses, archived | – |
| Property definition, naming pattern | The definition | `property_values` |
| Device | What it reported, its tabs, its camera layout | `devices`: fingerprint and type, for the automatic registration |
| Camera layout | Bars per orientation, look, options | – |
| Flow (extension) | Tracks, keyframes, markers | The extension's own tables for paired hardware and mesh networks |

**`refs`**: one row per pointer from a file to a file, with what kind it is (content entry, progression item, clip, overlay, base photo, placed picture, reference property) and its place in the order; for an item or a clip also its time and, where it points at one frame, the frame. It answers "where is this file used", shows missing references, and keeps a restore from the bin simple.

**`property_values`**: file, definition, value. Search, filters, the board and bulk edit work on it.

Kept as they are: `users`, `sessions`, `workspaces`, `workspace_members`, `projects` (plus the enabled extensions and the master timeline), `storage_daily`, `admin_settings`, `admin_audit`.

### Storage

Per photo three objects: the untouched original, a preview of about 2048 px, a thumbnail of about 400 px ([01](01-media.md)). Per canvas a render of the whole surface and a thumbnail ([05](05-composition.md)). A duplicate of a photo shares the stored objects.

## Target API

| Group | Routes | Notes |
| --- | --- | --- |
| Sign-in, `me`, workspaces | As today | Unchanged |
| Projects | List, create, rename, delete; extensions on and off; the master timeline | |
| Files | `GET /api/files` (a root, a container, a type, a query), `PUT /api/files/:id` (upsert, as today), move, bin, restore, purge, duplicate, release an internal file | One set of routes for every type; the body is checked by the type's own rules |
| Properties | Definitions (files in Settings); `PUT` values for one or many files; AI import | |
| Search and filters | A query over names and property values; saved as filter files | Replaces saved views |
| Media | Upload of thumbnail, preview and original, each idempotent; image delivery in three sizes | The queue's guarantees stay ([03](03-capture.md)) |
| Canvas | Save (body, frames, render in one request); the edit lock (take, renew, release) | The lock is general to files; the canvas is its first user |
| Devices and layouts | A device registers and updates itself; layouts are files of the account home | |
| Phone link | One connection per person with named channels ([08](08-extensions.md)) | Carries the layout preview; extensions register their channels |
| Extensions | Hardware: pairing, the catalogue, the proxy's channel, key backups. Flows: nothing beyond files | Own routes and tables, no column on a core table |
| Admin plane | As today | Unchanged |

Rules carried over: ids from the client, PUTs are upserts, uploads are idempotent, the server accepts stale references instead of rejecting them, interactive edits are checked strictly and uploads leniently, every route has a tenancy test.

## Teardown

1. **Before anything is deleted:** the owner downloads `/photos` from the production media bucket.
2. Production data is dropped: database and buckets are created new for the rebuild. Staging gets the rebuild first.
3. A new migration baseline replaces the 36 numbered files.
4. The Android signing key, the package id and the deployment repository are untouched: the rebuilt app updates the installed one.
5. Old code is removed area by area as its replacement lands (see the build order), not in one sweep, so `make check` stays green throughout.

## Build order (proposal)

Each step is a sub-issue of a new build epic and ends with something that can be used on staging. Vertical: server, Studio and phone together where a step needs them.

| Step | What | Done when |
| --- | --- | --- |
| B0 | **Ground**: build branch, new schema baseline, the `files` table with `refs` and `property_values`, file routes with tenancy tests, the shared model package | A file can be created, listed, binned and restored through the API |
| B1 | **Studio shell on the design system**: desktop, windows, `Dock`, launcher, the one browser with list and grid, the recycle bin | Folders can be made and browsed in the new Studio |
| B2 | **Media**: upload pipeline with three sizes, EXIF and angle of view, the Photo app, collections, import in the Studio | Photos uploaded in the Studio show in Media with their facts |
| B3 | **Phone shell and camera**: tabs per device, gates, Setup, the base camera with real lenses, the queue, Media on the phone, device registration | A photo taken on the phone appears in the Studio |
| B4 | **Properties**: catalogue, field types including reference and position, naming patterns, search, filters, board, bulk edit, AI import | A project's shot list template can be defined and filled |
| B5 | **Optics and canvas**: presets with the create flow and example photos, the canvas tool, frames, renders, the edit lock, the editor in a web view on the tablet | A photo can be framed, drawn on and seen on the phone |
| B6 | **Shots, sets, locations**: the three windows, content, progression with generator, internal files, the map view | A shot list with pictures and a zoom exists |
| B7 | **Timeline**: clips, playback, chapters, the master timeline, editing in place | A scene can be cut and played |
| B8 | **Camera layouts and devices**: bars, the layout editor, the phone link with channels and live preview, the optics frame in the camera, collection mode, the folder for new photos | A layout made in the Studio runs on the phone |
| B9 | **Hardware extension**: the extension mechanism, the catalogue, every existing driver, the proxy, Devices in both clients | Every light, battery, camera and transmitter of today is controlled as today |
| B10 | **Flows extension**: flows as files, the editor on every client, run on phone | Every sequence feature of today works |
| B11 | **Cutover**: docs rewritten, `packages/ui` and leftovers removed, release to staging, then production | Production runs the rebuild |

B0–B3 give the first end-to-end use (take a photo, see it in the Studio). B4–B7 are the planning tools. B8–B10 bring back what the current app is used for on set.

## Questions put to the owner

All four are answered under Decided.

1. **Where the build happens.** In this repository on a long-lived branch, with `main` kept releasable until the cutover, or directly on `main` with the current app broken from the first step.
2. **The order.** As above (the end-to-end photo path first), or the on-set tools (camera with optics frame, lights) first because they are what is used today.
3. **The database.** A new baseline and new databases, as proposed, or additive migrations on the existing ones.
4. **Documents as JSON.** A canvas's objects, a flow's tracks and a layout's bars stored as one checked JSON body per file, with tables only where the server must search (frames, references, property values), as proposed; or everything in columns and rows.

## Decided

2026-11-23, by the owner:

- **The rebuild is built directly on `main`.** Today's app cannot be released from `main` again once the first build step lands; production keeps running the last release until the cutover, staging runs the rebuild. `rewrite/plan` is merged into `main` before the first step.
- **The order is the proposed one:** the photo path first (B0–B3), then the planning tools (B4–B7), then camera layouts, Hardware and Flows (B8–B10), then the cutover.
- **A new schema baseline** on newly created databases and buckets; the old migration files go.

- **Tables for what is searched, a JSON body for what is saved whole,** as set out below.

Taken from the proposal with the above: the target data model and API, the map of today's tables, route groups, Studio apps, phone screens, feature pages and packages, the teardown list, and the twelve build steps B0–B11.

### Tables and JSON bodies

Normalise what the server searches, joins or has to keep consistent across rows; keep as one JSON document what is always loaded and saved whole.

| In tables | Why |
| --- | --- |
| Files, references between files, property values, photos and their stored objects, frames, devices | They are searched, filtered, joined or counted: "where is this used", "shots by set", "is this lens in use" |

| As a JSON body | Why |
| --- | --- |
| A canvas's objects and comments, a flow's tracks and keyframes, a layout's bars, a shot's progression settings | One editor at a time loads the whole and saves the whole; the server never asks for one object or one keyframe. Rows would mean hundreds of writes per save and a migration for every new property of an object |

How the usual weaknesses of JSON are met: every body is checked by shared code on every save (as layers, sequences and layouts are today); a body carries a version number and is upgraded when read, so a change to its shape needs no database migration; if the server ever has to search inside a body, that part moves into a table then. A limit to check in B0: how large a row the database accepts, for a canvas with very many pen strokes.

## Build notes

Findings of the build that the plan asked for or that change it. The specification above stays as decided.

- **B0, row size** ([#372](https://github.com/OpenClapper-dev/core/issues/372)): D1 takes at most 2 000 000 bytes per string and per row. A file's body is limited to 1 500 000 bytes of JSON. A canvas (B5) that could outgrow this stores its strokes compactly or moves the large part out of the row.
- **B0, the root of a file:** stored as two columns, a project or the user whose account home it is, instead of one `root` column, so both have a real foreign key.
- **B0, references:** a file's references travel with the file (`refs` in its save) and are stored in `refs`; a type's rules say which kinds it keeps. The server keeps a reference to a file it cannot find, and reports it as missing.
- **B0, shortcuts:** a file type of their own (`shortcut`: an app, or one reference to a file), since the Desktop folder's icons include shortcuts ([07](07-organisation.md)).
- **B0, types:** the shared model is a new package, `packages/model`; `packages/vocab` stays for the first app's clients until they are rebuilt and goes at the cutover. Each build step registers the file types it builds.
